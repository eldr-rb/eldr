** #6 Builder use-after-map — Eldr already matches Rack
The two implementations are line-for-line equivalent here. Verified
empirically:

#+begin_src ruby
# use AFTER map
Eldr: {"/" => {"content-type"=>"text/plain", "x-mw"=>"after"}, "/cats" => {"content-type"=>"text/plain"}}
Rack: {"/" => {"content-type"=>"text/plain", "x-mw"=>"after"}, "/cats" => {"content-type"=>"text/plain"}}
#+end_src

=Rack::Builder#use= also consumes the pending =@map= and pushes a
=generate_map= proc, so middleware added after a =map= wraps only the default
(=run=) app; middleware added *before* =map= wraps the whole =URLMap=; and a
=use= inside a =map= block is scoped to that block. The TODO's premise
("upstream scopes =map= separately") is inaccurate — this is upstream
behavior. Recommended outcome: *keep semantics, add parity tests, document*.

** #5 Matcher unsupported paths — real gap
=lib/eldr/matcher.rb:20= =case @path= has no =else=, so a non-String /
non-Regexp path silently yields =nil= and later raises an opaque
=NoMethodError= on =#match=. Making it raise =ArgumentError= is a small,
correctly-scoped behavior change. Coverage nuance: because the gate is
=line: 100, branch: 100=, the fix must leave every branch exercised (see
Phase 5 for the exact shape that keeps 100%).

** #2 Performance — measured baseline available

| Path                                   | Per call |
|----------------------------------------+----------|
| =BenchApp.call(env)= (public entry)      | ~5.7 µs  |

bottleneck despite being rebuilt on every =call=.

* Decisions to Confirm

1. *Docs generator*: YARD (add =yard= dev dep, =@param=/@return= tags,
   =rake yard=, CI docs job) vs stdlib RDoc (no dep). *Recommend YARD.*
2. *Matcher validation timing*: eager in =Matcher#initialize= (fail fast) vs
   lazy in =#handler= (minimal diff, matches TODO wording). *Recommend eager
   in =initialize=* plus a single ternary in =#handler= so branch coverage
   stays at 100%.
3. *Builder semantics*: keep Rack parity (recommended) vs change so
   middleware always wraps mapped apps (breaking, diverges from Rack).
4. *Wiki hosting*: in-repo =docs/wiki/= sources + manual/Rake push to the
   GitHub wiki, vs GitHub Pages, vs wiki-only. *Recommend in-repo sources +
   =rake wiki:publish= + README link.*
5. *Performance scope*: recognizer + params only (safe, measurable) vs a
   deeper rewrite (out of scope). *Recommend the former.*
6. *CI*: add a docs build + (non-gating) benchmark job, or keep CI as-is and
   run benchmarks locally. *Recommend a docs-build gate; benchmarks local.*

   versions, ips ± stddev). Do not gate CI on benchmarks (too noisy).

*** 2b. Optimize (behavior-preserving, coverage-safe)
1. =Recognizer#call=: replace =routes[verb].reject { ... }= + =sort!= with a
   single pass that pushes matches into an array, and only =sort_by!(&:order)=
   when the result has more than one element. Memoize =pattern= per env (or
   inline =PATH_INFO= handling) and avoid re-computing =verb= via
   =downcase.to_sym= when unnecessary. Prototype measured ≈14% faster on the
   routing benchmark.
2. =Route#match= / =Matcher#match=: short-circuit and avoid the extra method
   hop where safe; keep the memoized =@handler=.
3. =App#call!= parameter handling: avoid forcing =Rack::Request#params=
   (query-string parsing) when a handler never reads =params=. Preferred
   shape: merge route captures into =env['eldr.params']= directly and make
   the =#params= reader the single place that lazily merges
   =request.params=. Keep =env['eldr.params']= populated as today so the
   existing spec (=app.env['eldr.params']['id']=) stays green. If this cannot
   be done without an observable behavior change, drop it and rely on #1–#2.
4. =Builder#to_app=: optional cache so =Builder#call= does not rebuild on
   every dispatch (note: upstream =Rack::Builder#call= also rebuilds and
   documents this; =to_app= is cheap at ~0.19 µs, so treat as low priority).
5. Re-measure; keep an optimization only if it is ≥10% on its target
   benchmark and keeps the suite green at 100%/100% coverage.
6. Add a regression spec only where behavior is subtle (e.g. recognizer
   ordering with equal/multiple orders); do not add timing assertions.

*** 2c. Document
1. Replace the stale 2015 bench-micro table in README =Performance= with
   current numbers and a short note that a repeatable suite lives in
   =benchmarks/= (=rake bench=). Keep the bench-micro link as an external
   cross-check.
2. CHANGELOG "Changed" entry describing the optimization.

** Phase 5 — Matcher raises ArgumentError (=TODOS #5=)

Deliverable: fail-fast, typed error for unsupported path types, without
regressing the 100% coverage gate.

1. =lib/eldr/matcher.rb=:
   #+begin_src ruby
   def initialize(path, options = {})
     unless path.is_a?(String) || path.is_a?(Regexp)
       raise ArgumentError, "unsupported path type: #{path.class} (expected String or Regexp)"
     end

     @path    = path
     @capture = options.delete(:capture)
   end

   def handler
     @handler ||= @path.is_a?(String) ? Mustermann.new(@path, capture: @capture) : /^(?:#{@path})$/
   end
   #+end_src
   Rationale for the ternary (not =case/else=): eager validation makes the
   implicit =else= unreachable, which would leave an uncovered branch and
   fail the =branch: 100= gate. The ternary has exactly two branches, both
   covered by existing String/Regexp examples.
2. =spec/matcher_spec.rb=: change the "unsupported path types" example to
   assert the raise at construction:
   #+begin_src ruby
   it 'raises ArgumentError for paths that are neither String nor Regexp' do
     expect { described_class.new(:cats) }.to raise_error(ArgumentError, /unsupported path type/)
   end
   #+end_src
3. =spec/route_spec.rb= (optional but recommended): assert that a =Route=
   with an unsupported =path:= surfaces the =ArgumentError= when its matcher
   is first built (=route.matcher=), documenting that validation is lazy for
   routes. If fail-fast at route-definition time is preferred, also call
   =matcher= from =Route#initialize= (adds one line; keep coverage).
4. Docs: note supported path types (String Mustermann pattern or Regexp) in
   =Matcher= YARD docs and README Rails-style routing section.
5. Decide and record whether =path: nil= / symbols should be a route-definition
   error; if yes, validate in =App.add= too (small follow-up).
6. CHANGELOG "Changed/Fixed" entry. Check =TODOS #5= off.

green.

* Risks & Notes

1. *Coverage gate is strict (100% line + branch).* New lib code (Matcher
   validation, recognizer optimization, lazy params) must leave no uncovered
   branch. The ternary-in-=handler= shape is specifically chosen to keep
   branch coverage at 100%. Verify with =COVERAGE=1= after every lib change.
2. *Performance changes can regress under different Ruby versions.* Keep
   optimizations small and benchmark on the CI matrix before declaring a win;
   don't gate CI on timings.
3. *Lazy params can change observable env timing.* If making =App#params=
   lazy changes what is present in =env['eldr.params']= mid-filter, keep the
   current eager merge (or a hybrid) and rely on recognizer/route
   optimizations instead.
4. *Matcher behavior change.* Raising =ArgumentError= is technically
   breaking; decide 0.1.0-vs-0.2.0 in Phase 7. Symbol/nil paths are almost
   certainly bugs in caller code, so impact is low.
5. *Wiki publishing needs credentials.* The wiki is a separate git repo;
   =GITHUB_TOKEN= is not reliably able to push it. Keep sources in-repo and
   treat the push as a manual release step (or use a PAT in a dedicated
   workflow).
6. *Docs tool choice adds a dev dep.* YARD is dev-only and does not affect the
   installed gem's runtime dependencies. The stdlib RDoc fallback keeps the
   dependency count at zero if preferred.
7. *README is a contract.* =spec/readme_spec.rb= + =readme_definitions.yml=
   must stay green; adding links/sections is safe (only boolean flags are
   asserted), but preserve existing headings the quickstart defines.
8. *Examples are excluded from RuboCop* (=.rubocop.yml= =examples/**/*=), so
   Cascade example tweaks won't trip lint; keep them Rack-3 valid (they run
   through =Rack::Lint= in the spec helper).
